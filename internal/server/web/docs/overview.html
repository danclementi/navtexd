1. What navtexd is

navtexd receives NAVTEX maritime safety broadcasts from an audio or I/Q stream. It decodes them, identifies the transmitting station, tags and logs every message, and presents everything via a web interface. It is a single self-contained program and was inspired by the Windows program YaND ("Yet another NAVTEX Decoder", by the late Dirk Claessens). It aims to provide useful enhancements to YaND wherever appropriate while maintaining ease-of-use.

Not for navigation. NAVTEX reception here is experimental and error-prone. Never rely on this software for navigation, weather routing, collision avoidance or any other safety-of-life decision. Use certified equipment and official sources.

2. Client and server

  • Client-server design. The "navtexd" program itself does all the decoding and keeps the log. It runs in a terminal window. It does not have a user interface of its own, but instead includes a server that you access from a web browser for viewing and control purposes. The browser can be on the same computer that navtexd is running, or from anywhere that can reach that computer.
  • Multiple clients simultaneously. The purpose of supporting multiple clients is to allow an instance of navtex to be viewed by others who may find the information useful; perhaps for log review, perhaps to examine real-time propagationconditions.
  • Two roles are provided. Administrators (direct connections from the local machine or a private network) have full access (i.e. including change of all program options, editing and deletion of log entries, database management, and so on). Viewers (anyone arriving through a proxy or tunnel, such as a Cloudflare tunnel) are limited but can still view real-time decoding and live channel spectra, select andread log entries, and even generate reports.
  • Light on the network. Remote viewers get a lively feed with very low WAN data usage because pages and data are losslessly compressed.
  • These Help files themselves are served by the program and are viewable by everyone, viewers included.

3. Inputs

  • Up to FOUR channels at once. One program decodes, tags and logs messages from up to four channels simultaneously. Each channel can have its own frequency, input source, and decoder settings.
  • Real or complex audio. A channel accepts real-valued audio (a receiver's audio output, a sound card or virtual audio cable, a WAV file, raw samples on standard input) or complex I/Q from SDR hardware.
  • Several channels from one I/Q stream. Channels can share one input if desired. A single 48 kHz wideband I/Q stream can, for example, feed a 490 kHz and a 518 kHz decoder at the same time.
  • I/Q over the network. The program can accept I/Q streams over Ethernet from Hermes-type receivers (using OpenHPSDR protocol 1: Hermes, Hermes Lite, ANAN and similar), from an Airspy HF+ through the SpyServer program, and from an SDRplay receiver through the headless SDRconnect server.
  • No calibration required. The carrier and the symbol timing are tracked continuously, so the sound card or SDR sample rate does not need to be calibrated.
  • Automatic polarity. The decoder detects and adapts, whether the audio signal is received in USB or LSB, selecting mark and space correctly.

4. Decoding

  • A streaming decoder: carrier search and tracking, symbol timing, SITOR-B framing, and combining of the two transmitted copies of every character.
  • Two framing methods can run side by side on different channels for comparison: hard (fast, needs a clean signal) and soft (locks later but works in more noise).
  • Unreadable characters are shown as ~. Optional spelling correction repairs them from a maritime vocabulary; the raw received text is always kept unchanged.
  • A message whose ZCZC was damaged is still recognised by its position and the identification group that follows.
  • Fragment dropping. Text received outside any message (mostly noise) is dropped unless it passes a vocabulary word test. The test and the vocabulary can be tuned, and you can add your own words.
  • Technical detail on how the decoder works, stage by stage, is in this section: How the demodulator works.

5. Monitoring

  • Thumbnail spectra are always visible at the top of every tab, so you can monitor activity while reviewing the log, generating reports, etc.
  • The Spectrum tab shows a large spectrum that can be zoomed and moved, with one trace for incoming spectrum and a second trace for the signal after the receiver's channel filter (which is what the demodulator actually sees).
  • Meters for input level, signal quality and CPU load, lock/sync/data indicators for each channel, and a ticker-tape display of the selected channel's live decode.
  • A System Log records what the program is doing, including a watchdog that reports an input that has stopped delivering samples.

6. The message log

  • Every message is stored with its time, channel, station, subject and serial number, in a log with filters (station, subject, text, distance) and de-duplication.
  • Multi-selection: Ctrl-click selects individual rows (i.e. log entries) and Shift-click selects a range. The selection can be reviewed, added to a report, or deleted.
  • Undo: deletions and edits can be undone, repeatedly, one step at a time. The undo history is kept on disk, so it survives a restart of the program (undo information is retained for 30 days).
  • Trash: deleted messages stay in the database for 30 days. The Database dialog lists them, with a search box, and brings back any of them in any order, whichever deletion they were part of.
  • Backups: before the log database is compacted, a backup copy is made automatically (the three newest are kept). Backups are also made before an import is made that would add to or replace the current log.
  • Messages are stored in one SQLite database file (messages.db) in the data folder, which other programs can open (the messages view is the readable table); all times are UTC.

7. Station identification

  • The B1 letter and the frequency do not name a station by themselves, so every message is scored against a station table (in YaND format). For each candidate station, the score combines unique keywords (the station's own name or call sign), geographical keywords (places named in its warnings, weighted by how few stations share them), the time slot, the distance from your position, and how often you have received that station before.
  • A station is named only when the evidence is clear. Otherwise the record stays unidentified and the ranked candidates with their scores are kept, so you can decide.
  • Review pane: in the reader pop-up you can assign a station ID to a record yourself, chosen from the stations scheduled at that time or any station which broadcasts on that frequency. Such an identification is marked as forced when the message text does not support it.

8. Reporting

  • Multiple log entries are easily selected and, with a single click, transferred for report generation. The complete report can be reviewed in a pop-up pane and the text can be edited as needed in place there.
  • Once reviewed, the report can be copied to the clipboard or saved as a file.
  • Currently, only YaND format is supported for report generation.
